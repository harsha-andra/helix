# HELIX — Policy & Claims Platform

An enterprise insurance operations UI built in Angular 19: claims intake, a multi-step
claim wizard, policy and claimant lookup, and an operations dashboard. It runs entirely
client-side against a seeded in-memory demo API, so it's fully functional as a static
deployment with no backend — while every request shape matches a real Spring Boot
`/api/v1` contract (see below), so swapping the demo interceptor for a live backend is a
one-line change.

## Quick start

```bash
npm install
npm start        # ng serve, http://localhost:4200
```

Sign in with **any** name/password — demo mode accepts anything — and pick a role
(Adjuster, Manager, or Viewer) to see role-based access in action.

```bash
npm run build     # production build -> dist/helix-web/browser
npm test -- --watch=false --browsers=ChromeHeadless
```

## Demo mode

`environment.demoMode` (on by default in both `environment.ts` and
`environment.development.ts`) turns on `demoApiInterceptor`, an `HttpInterceptorFn` that
intercepts every `/api/v1/*` call and serves it from `DemoDataStore` — an in-memory,
mutation-aware store seeded with:

- **60 claims** (`CLM-2025-XXXXXX`), **25 policies** (`POL-2024-XXXXXX`), **40 claimants**,
  and a handful of adjusters — generated with a seeded PRNG (`seed-data.ts`) so the dataset
  is deterministic within a session but reads as authentic US insurance data (real-looking
  names, cities, coverage codes, incident narratives).
- Genuine pagination, status/text filtering, and sorting on the claims and policies lists —
  the interceptor parses `page`/`size`/`status`/`q`/`sort` query params and slices/filters/sorts
  the seeded array, just like a real backend would.
- Claimant typeahead (`/claimants/search`) that filters by name, email, or city.
- Mutations that persist for the session: submitting the claim wizard adds a real claim to
  the list; changing a claim's status updates it in place (with a 200–500ms simulated
  network delay on every call).
- **One planted failure**: the claim whose number happens to be the API contract's own
  example, `CLM-2025-004417`, always rejects its status-change request with a 409 "modified
  by another user" conflict. That's what the optimistic-update rollback on `/claims/:id` is
  built to demo — open that claim, change its status, and watch it flip immediately, then
  snap back with an error snackbar a moment later.

To point the app at a real backend instead, set `demoMode: false` in the environment file
and remove `demoApiInterceptor` from `app.config.ts`'s `provideHttpClient` call — every
service already speaks the real `/api/v1` contract.

## Project structure

```
src/app/
  core/            # models, API services, interceptors, guards, demo data store + seed data
  store/            # NgRx feature slices: claims, claimants, wizard (actions/reducer/effects)
  shared/          # status chip, skeleton loader, empty/error state, page header, pipes
  features/
    shell/         # sidenav + toolbar shell (breadcrumb, search, notifications, theme toggle)
    dashboard/     # KPI cards, claims-by-status breakdown, recent activity feed
    claims/        # paginated/filterable/sortable claims table
    claims-detail/ # claim header, status-change action, Overview/Lines/Documents/Audit tabs
    claim-wizard/  # 5-step NgRx-backed claim submission wizard (steps/ subfolder)
    policies/      # policy list with expandable coverage rows
    claimants/     # typeahead claimant search
    login/         # demo sign-in
    not-found/     # 404
src/styles/
  _tokens.scss     # design tokens: color ramps, spacing, radii, elevation, type scale
  _m3-palettes.scss# custom M3 tonal palettes built from the tokens (see below)
  _theme.scss      # Angular Material M3 theme assembled from the palettes
```

## Design system

`src/styles/_tokens.scss` holds the design tokens extracted from the Figma "HELIX Insurance
Dashboard" design system file — spacing scale, radii, elevation, and type scale as CSS custom
properties, plus semantic color roles (surface/border/text, status chip colors) that stay
consistent between light and dark mode.

The Material theme itself (`_theme.scss`) is a genuine custom **M3** theme, not a stock
Material palette: `_m3-palettes.scss` defines full M3 tonal palettes (13 tone stops per
ramp, plus the secondary/neutral/neutral-variant/error sub-ramps `define-theme` expects) for
a **deep indigo primary** and **teal tertiary/accent**, generated by re-synthesizing
Angular Material's own tone → lightness curve at HELIX's brand hues rather than reusing any
of Material's bundled violet/rose/azure palettes — i.e. never the default Material
purple/pink. Dark mode is a runtime toggle (`ThemeService`, persisted to `localStorage`) that
flips a `data-theme` attribute on `<html>`; both the Material theme and the token layer
define an explicit dark variant rather than relying only on `prefers-color-scheme`.

Every list/table has a skeleton-loading state, a real empty state, and an error state with
retry (`shared/components/empty-state`, `shared/components/skeleton`) — no raw `undefined`
in the UI. The layout is responsive down to 360px: the sidenav becomes an overlay drawer on
handset widths, and data tables reflow into stacked cards via CSS (`data-label` attributes +
a media query), rather than just shrinking columns until they're unreadable.

## NgRx & RxJS decisions

- **Claims** (`store/claims`) uses a `@ngrx/entity` adapter for the paginated list, plus a
  separate `selectedClaim` slice for the detail view. The status-change action
  (`ClaimsActions.updateStatus`) is handled with a genuine **optimistic update**: the effect
  dispatches `updateStatusOptimistic` first (the reducer patches the entity — and the
  selected claim detail, if it's the same one — immediately, while snapshotting the previous
  value), then fires the real request. On success the snapshot is discarded; on failure the
  reducer restores the snapshot and a snackbar surfaces the rejection. This is exercised for
  real by the one deliberately-failing demo claim described above.
- **Claimants** (`store/claimants`) is a small search slice shared by the standalone
  `/claimants` page and step 2 of the wizard.
- **Wizard** (`store/wizard`) is the resume-relevant piece: the entire multi-step form's state
  — current step, per-step field values, and which steps are complete — lives in a dedicated
  NgRx feature slice, not component fields. Because the slice is registered once at the root
  (`app.config.ts`), navigating away from `/claims/new` and back preserves every step's
  progress without needing to touch `localStorage` at all — that's only used for the explicit
  "save draft" / "resume draft" feature (`WizardPersistenceService`), which is for surviving a
  full page reload, not in-app navigation.

  Validity and step-reachability are **derived selectors**, not stored booleans — a step's own
  field data is the single source of truth for whether it's complete, so there's no way for a
  cached "is this step done" flag to drift out of sync with what the user is actually editing.
  `selectIsStepReachable(n)` gates whether step `n` can be jumped to (step 0 is always
  reachable; step `n>0` requires every step before it to be valid), and both the Angular
  Material stepper (`linear` + per-step `[completed]` bindings) and the wizard's own
  "Next" button consult it.

- **Typeahead cancellation, twice over**: both the policy search in wizard step 1
  (`WizardEffects.searchPolicy$`) and the claimant search shared by wizard step 2 and the
  `/claimants` page (`ClaimantsEffects.search$`) use the exact same
  `debounceTime(300) -> distinctUntilChanged() -> switchMap(...)` pattern in an NgRx effect,
  with an explicit comment at each call site: `switchMap` cancels whatever request is still
  in flight for the previous keystroke, so a slow response for `"sm"` can never land after
  (and overwrite) the fresher results for `"smith"`.

## Security touches

- `authInterceptor` attaches `Authorization: Bearer <token>` (a locally-generated demo token)
  to every outgoing request, mirroring how the real backend's OAuth2 resource server expects
  requests to be authenticated.
- `roleGuard(...roles)` is a `CanActivateFn` factory; `/claims/new` is guarded to
  `ADJUSTER`/`MANAGER` roles. The same underlying `AuthService.hasRole('ADJUSTER')` check is
  reused component-side to disable the claim status-change control for any role that isn't
  `ADJUSTER`, so the rule is enforced consistently rather than only at the route boundary.
- No `innerHTML` is used anywhere with unsanitized (or any) input; all dynamic text goes
  through Angular's normal interpolation/contextual escaping.

## Tests

Jasmine/Karma specs cover the claims reducer (entity updates, the optimistic-update/rollback
path), the wizard reducer (step navigation, per-step validity gating, draft restore), the
claims effects (`loadClaims$`, and `updateStatus$`'s optimistic-then-confirm/rollback
sequence via `provideMockActions`/`provideMockStore`), and one component
(`DashboardComponent`, covering its loading/error/loaded states and derived KPI values).

Headless Chrome needs `--no-sandbox` to launch as root (this sandbox, many CI containers).
Rather than requiring a special browser name, `karma.conf.js` points `CHROME_BIN` at
`scripts/chromium-no-sandbox.sh`, a wrapper that execs the real browser
(`/opt/pw-browsers/chromium` here, or a `google-chrome`/`chromium` found on `PATH` elsewhere)
with `--no-sandbox` appended — so the plain, standard invocation works everywhere:

```bash
npm test -- --watch=false --browsers=ChromeHeadless
```

34 specs, all passing.

## Deploying (Vercel)

`vercel.json` sets `outputDirectory: dist/helix-web/browser` (Angular 19's application
builder output path) and rewrites every route to `index.html` for client-side routing. No
serverless functions or environment variables are required — the whole app, backend
included, runs in the browser via demo mode.

## Known gaps

- Document "upload" in the wizard and on the claim detail page is metadata-only (file name,
  type, size) — no bytes are read or stored, by design for a stateless demo.
- The claimants/policies lists use direct service calls with local component state rather
  than a dedicated NgRx feature store; only claims, claimants (search), and the wizard were
  built as NgRx feature slices, per the brief.
- `/adjusters` is implemented end-to-end in the demo API and `ClaimantsApiService`, but
  there's no dedicated adjuster-management screen — adjusters are auto-assigned when a
  demo claim is created.
